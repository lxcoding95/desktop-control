# S02 native identity boundary

2026-10-24 implementation under completion authorization; no expansion into session5 enrollment/UI.

Windows: repository-owned C# helper reads the **Node caller process** token via fixed numeric PID, limited process query and TOKEN_QUERY. It uses OpenProcessToken/GetTokenInformation and WindowsIdentity only; closes every handle/unmanaged buffer. A fixed absolute executable derived from module location is invoked without shell, with2s timeout,4KiB output bound, hidden window, no user-selected command. Missing/malformed/failing helper returns null. No SID may be emitted in public evidence/audits.

Accepted token: local/domain account SID S-1-5-21..., exact caller PID, medium integrity8192, not elevated, UIAccess false, interactive session>0. Other SID families (including untested AzureAD identities), elevated/high-integrity, low-integrity, service/session0 fail closed. This is an explicit tested support restriction, not a promise of universal Windows identity support. Build requires existing .NET Framework4 compiler; build output is local and not signed/released. Buildchain/code paths are trusted host material, not untrusted MCP input.

Linux: matching actual UID/eUID>0 yields posix UID. UID0 or mismatched real/effective identities returns null. Native negative probes run against actual kernel IDs:0/0,1000/0,0/1000; each null principal/PERMISSION_DENIED/zero adapter invocation. The differing-ID probes use temporary offline, read-only containers with only CAP_SETUID, no Docker socket, no host elevation and the existing image/repository volume. They are disposable probes, not a replacement development environment. This establishes UID boundary behavior, not a general Linux capability/namespace sandbox proof.

The principal is only one input to the host policy. Production server startup always injects an empty grant store. The existing explicit trusted host programmatic seam accepts exact scoped temporary grants, and tests prove both allow and deny with the native process identity. A separate client cannot enroll grants via MCP/args/environment. Persistent host consent/OS-protected storage and UI remain future session5 work under the original contract, not silently accepted here.

Evidence so far: real Windows SID matches WindowsIdentity without logging the value; normal-token positive/negative host-grant tests pass. Elevated/service/malformed token snapshots are rejected by parser tests. A **real elevated Windows process negative test has not yet been executed**; do not conflate parser tests with UAC evidence. Required targeted owner action, if that remains a binding gate: run the prepared bounded identity-only elevated probe, not the whole assistant as administrator.
